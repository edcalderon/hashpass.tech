# Version drawer: stale "Git Commit" field (fixed 2026-07-31)

**Status: fixed on `develop`, not yet in a shipped release.** The version
drawer's/quick-sheet's "Git Commit" link has been showing the wrong commit
— frozen at `391a21b64` (a 2026-07-12 mobile-native-auth commit, completely
unrelated to the version being displayed) — for every release since
`06f3f736f` synced it to v1.8.209. Confirmed still wrong in the live
v1.8.292 production bundle at time of writing (`grep`'d the deployed JS for
the stale hash directly).

This was found while investigating a user report that the update-modal's
"Update Now" flow wasn't reflecting the new version after reload — that
specific complaint turned out to be deploy-timing (the screenshot was taken
while the `hashpass-production-site` CodePipeline execution for v1.8.292 was
still running; verified after the fact that production correctly served
v1.8.292 with a fresh, uncached `index.html` once the pipeline finished, see
[`CDN_CACHE_BUSTING_HPV.md`](../../infra/CDN_CACHE_BUSTING_HPV.md) for the
CDN-side fix from the same investigation). This "Git Commit" staleness is a
**separate, real, and independently-confirmed bug** found along the way.

## Root cause

Two independent facts combine to break this field:

1. `packages/tools/scripts/release.js`'s `runMainRelease()` (the function
   `release:promote` uses) called `update-version.mjs` with
   `--skip-git-info`, which — per `update-version.mjs:874` — skips the
   entire block that writes `apps/mobile-app/config/git-info.json`. So this
   file has not been regenerated by any release since `06f3f736f`, no matter
   how many versions have shipped since.
2. `version-service.ts:77-104`'s `getBuildInfo()` does have a fallback path
   that would use `process.env.EXPO_PUBLIC_RELEASE_COMMIT` or
   `process.env.GIT_COMMIT` instead — but nothing in this repo's CI
   (workflows, buildspecs, or build scripts) ever sets either variable, so
   that fallback is dead code. The static, never-refreshed
   `git-info.json` value is therefore the only thing that ever populates
   this field, and it always wins over the (unused) env fallback because
   `getBuildInfo()` checks the static file first.

## Fix

- `packages/tools/scripts/release.js`: removed `--skip-git-info` from the
  `update-version.mjs` call, so `apps/mobile-app/config/git-info.json` gets
  regenerated with the real `git rev-parse HEAD` (captured just before the
  version-bump commit, same as the mechanism's original 2026-06 design —
  see `update-version.mjs:874-914`) on every future `release:promote` run.
- `apps/mobile-app/config/git-info.json`: manually regenerated once to the
  actual current commit, to stop shipping the three-week-stale value while
  waiting for the next real release to self-correct it.

No change was made to `version-service.ts`'s env-var fallback order — it's
unused in practice (nothing sets those vars) but harmless to leave as a
defensive fallback if a build pipeline ever wants to inject a commit hash
without going through `git-info.json`.

## Verifying after the next release ships

```bash
curl -s https://hashpass.tech/ -o /tmp/index.html
grep -o '/_expo/static/js/web/index-[a-f0-9]*\.js' /tmp/index.html
# fetch that bundle URL and grep for the expected short commit hash —
# it should match the release commit, not a stale unrelated one.
```
